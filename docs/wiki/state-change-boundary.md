# 状态改动的边界（State Change Boundary）

读与写的边界不对等：`game/entities` / `events` / `memory` / `tools` 只放基建原语，任何模块都可以读；一旦要改记忆或 ECS，就必须发生在 `game/systems` 的 mixin 里。

## 为什么是 mixin

mixin 同时是提示和限制。继承它就等于声明「这段代码在某个 system 的执行链上」：知道自己跑在哪一轮、因为哪个动作、被谁触发。反过来，控制台、服务端路由、工具函数里如果想直接改状态，手上没有入口——只能绕过去，而绕过去这件事本身是可被检查的。

判据不在「谁能改」，而在「改的时候是否知道上下文」。pipeline 就是那个上下文：一轮的开始与结束、动作何时被消费、失败时回滚到哪，只有 system 知道。

## 例外只有四类，外加回滚

创建（装配世界）、销毁、发动动作（接管与点名计划）、绑定（入场前的席位配置）都不进 pipeline——它们描述的是「一轮之外」的配置与终止，不是「这一轮里世界怎么变」。回滚同理：它是生命周期把世界拨回某个快照，而不是一次叙事进展。

能说清属于哪一类，就可以例外；说不清，就是越界。维护类的记忆操作（例如手动压缩）不在此列：它同样表达为一个动作，由 system 在 pass 内消费，于是失败也能整次回滚。

## 守卫的形状

静态检查扫描未被豁免的模块，命中「改实体」或「改记忆容器」就失败，并要求把例外写进一张带类别的表。识别靠变量命名约定（改实体时用 entity / actor 这类名字），这是刻意的取舍：它挡的是无意，不是恶意——别名、间接引用绕得过去。

真正的强制力来自类型：写入口只挂在 mixin 上，绕过它需要额外的意图。

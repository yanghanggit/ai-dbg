# 服务端客户端（ai-srpg-client）

## 定位

`ai-srpg-client` 是第二种运行与验证方式：进程内经 HTTP 驱动常驻服务端。它与离线的 `ai-srpg-agent-game` 平级——共用同一套 pass、快照与回滚语义，区别只在传输与并发边界：离线路径在一个进程里直接读写存储，客户端把房间锁与队列交给服务端。

客户端服务于端到端验证与远程驱动，不承载开发期观测能力；prompt 检查、调用留痕与记忆压缩仍在离线路径。

→ 参见：[SRPG AI 操作 CLI（ai-srpg-agent-game）](run-agent-game.md)

## 契约

传输契约由服务端定义并被两端共用：请求与响应模型只有一份，客户端不复制领域模型。根路由给出服务自描述与路由清单，OpenAPI 文档给出全部路径与分组，因此新增接口时客户端只需接线，不必重新对齐字段。

## 生命周期

房间（会话容器）与游戏局是两个生命周期：先进入房间，再开局。离开房间只清理进程内状态与锁，已落库的快照与会话历史保留，因此同一对局可以重进、可以换客户端观察。身份在无鉴权阶段就是路径里的用户名；这一阶段的服务端不应暴露到不可信网络。

→ 参见：[用户会话历史（PlayerSession）](session-history.md)

## 异步边界

推进不是同步请求：客户端只拿到 job 标识，执行由服务端后台完成。进度以队列状态与 job 事件为准，客户端不推断状态；等待超时只表示「仍在执行」，不表示失败。一次成功推进会在执行前（回滚基线）与成功后（当前状态）各写一条快照，因此最新快照就是服务端此刻的世界，重启不丢轮次。连续推进是客户端侧的循环，服务端不内置玩法循环，定时触发留给玩法规则落地。

→ 参见：[Job 执行与事件日志（Job Execution）](job-execution.md)

## 命令面

`info` 打印服务自描述与路由清单。`enter` 进入房间，`state` 查询状态，`leave` 离开。`open` 开局——加载最新快照，没有快照则从蓝图新建，重复调用幂等。`advance` 派发一次 pass 并默认等待终态，`--no-wait` 只返回 job 标识。`play` 自动进入房间与开局，再连续推进指定轮数，每轮打印 job 状态与最新快照，任一轮未成功即中止。`snapshots` 列出快照元数据，`messages` 按序号增量读取会话历史，`job` 查看单个 job 的状态与事件。

对局以「用户 + 游戏名」定位，同一组参数在离线 CLI 与客户端之间通用；`--json` 输出原始契约对象供脚本消费，服务端地址可由环境变量提供。

## 与其他系统的关系

- 服务端路由只做收发与前置校验；玩法与存储规则不在这一层。
- 会话游标、job 状态与快照元数据均由服务端提供，客户端只做解析与呈现。
- 世界状态只经服务端的只读接口访问，客户端不加载 ECS。

# 描述刷新（Description Refresh）

## 结论

角色的外观与舞台的环境是同一形状的两对数据：一份内容侧写定的**底稿**，一份进游戏后会变的**当前描述**。底稿永不改写，当前描述由 LLM 依据该实体自己的 agent 记忆重写。因此「这个实体现在看起来是什么样」始终只由一处真相回答。

## 两条路径，一个入口

刷新由一个只在当轮有效的动作组件驱动，收集与消费分处两端。

自动路径在收集端做状态守卫：当前描述仍等于底稿时才挂动作。写完一次，两边就不再相等，下一轮自然不再挂——自动刷新因此是幂等的，不会每轮重写同一段文字。

主动路径是直接挂同一个动作：守卫只拦自动路径，不拦写入方。战斗结束、装备更换这类需要强制重刷的场合，由玩法自己挂动作即可，不必给刷新链路加参数。

动作只活一次 pass，收尾统一清除，这保证了「刷新是一次显式状态变更」，而不是藏在某个组件里的待办标记。

## 两种描述的长度不同

外观是一张**定格快照**：只写照片里能看见的部分。它不写动作与场景，也不出现名字——一旦写出「他蹲在火旁」，描述就变成了叙事片段，而它本该回答「这个人现在看起来是什么样」。

环境描述的是**舞台自身**：空间、光、声、气温、气味，以及固定在其中的东西。角色的存在与作为一律不写——一旦环境里出现角色的影子，角色状态就有了第二个来源。

判据必须用引擎概念（角色 / 舞台）表达，而不是题材概念。用「自然」划界在荒野题材成立，换成机库或舱室就不成立：那些地方每一寸都是人造物，但仍然是舞台自身。

两条提示词都按原理写，不列举具体物件：例子一旦写死，就成了某个故事的场景清单，换题材即失效。

## 写回时也写记忆

改写沿用实体自己的 agent 记忆作为上下文，因此新描述只存在于组件里时，记忆中的「我原本长什么样」还是旧设定，之后的推理会把两者混用。所以刷新成功后还会往该实体记忆里补一条确认消息，把当前描述与底稿并排放在一起：一个说明此刻的样子，一个说明它不随状态改变。

## 失败的出口

生成失败或输出为空时什么都不写：底稿不动，下一轮守卫会再次挂上动作，等于自动重试。这符合「system 自行处理预期内失败」的边界，不进回滚。

→ 参见：[System 错误处理与回滚边界](system-error-handling.md)

## 边界

刷新只改当前描述，不改底稿、不改记忆、不发布领域事件。它消费的是记忆里已经发生的事，因此必须排在产生事件与广播的 system 之后。

→ 参见：[内容无关引擎（Content-Agnostic Engine）](content-agnostic-engine.md)

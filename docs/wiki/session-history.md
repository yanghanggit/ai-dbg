# 会话历史（Session History）

会话历史记录「这一局里发生过什么」：领域事件按发生顺序追加，不随游戏实例重建而重置。它与快照分工明确——快照是可重建的当前状态，历史是不可回滚的已发生经过。

## 设计意图

- **按局归属**：历史属于一局游戏（房间），而不是某个人。同一局里所有玩家读的是同一条流，因此不会出现「同一件事写 N 份、序号各算各的」。
- **每人一个游标**：每个玩家只记自己在流上读到哪，进房即停在流头（"加入即已读"），之后按自己的进度增量读取。
- **可见性随事件**：流水线上每条事件可以声明为全房可见或只对某个玩家可见，因此多人局的私密信息（只该某人知道的发现）不必另开一条流。
- **append-only**：每条事件只追加、不重写，局内序号单调整增。
- **当前上下文与历史分离**：玩家会话上的当前游戏与角色只是上下文指针；每条消息自行记录产生时的游戏、角色与 job，避免跨局后无法解释历史。
- **失败尝试也进入历史**：失败的 job 可以重试或丢弃，但已发生的尝试仍是已发生经过的一部分；客户端通过 job 标识与结果区分成功历史与失败尝试。
- **非游戏状态**：会话是叙事与事件历史，不是 ECS 状态，不能用来重建游戏。

## 持久化边界

历史消息落在 `session_messages` 表：一行一条，按局（`room_id`）分配递增序号，只追加不更新；可见者为空表示全房可见。内存中的玩家会话只保留两样东西——自己在流上的已读游标与当前游戏/角色指针；因此房间回收、进程重启都不影响历史，增量接口直接按序号读库，游标由调用方传入。

会话不参与快照回滚：快照只回滚 ECS 与 agent 记忆，已发生的领域事件仍是已发生经过的一部分。分页、归档与查询属于存储层职责，不改变事件语义。

序号由房间在内存里分配，因此一局同一时刻只应有一个写入者（当前是单进程房间 + 单 worker 的部署形态）；多写入者需要把序号分配下沉到存储层。

## 与其他系统的关系

- 领域系统只向游戏实例的事件出口发布事件；会话作为订阅者接收，因此领域层不知道会话的存在。
- 新局只替换游戏实例，沿用同一条流；房间关闭与空闲回收只丢弃内存游标，历史仍在库中，重进房间即可按序号续读。
- 历史与快照对「归属」的认定一致：两者都按局标识，所以换人观察、换进程读取都指向同一局。

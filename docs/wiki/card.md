# 卡牌数据模型（Card）

---

## 定位

`Card` 是战斗行动的最小单元。字段按「谁来消费」分为三层：确定性骨架、语义数据（词缀）、生命周期流转。三层职责正交，但当前只有确定性骨架与生命周期进入战斗结算。

---

## 确定性骨架（计算端消费）

`name` / `description` / `cost` / `damage` / `hit_count` / `block` / `target_type` 构成牌的确定性底座。

`cost` 由出牌执行端扣减 energy；`damage` 与 `block` 在牌进入战斗牌堆时叠加角色攻击/防御，之后分别参与伤害结算与持有期防御；`target_type` 决定目标解析策略——单个目标、阵营锚点展开、阵营散射、锁定自身四种语义。

`name` 是标识与决策的匹配键；`description` 是叙事锚点，也作为静态结算广播的演出文本，不改变数值。

---

## 语义词缀（数据保留，当前不参与结算）

五组词缀 `on_play_affixes` / `on_hit_affixes` / `on_turn_end_affixes` / `on_autonomous_affixes` / `engine_affixes` 是自由文本 `[词缀名]:机械结算描述`，分别标记出牌、被命中、回合结束、自主运行、运转（牌堆层面）五个触发时机。

这些字段目前只作为卡牌数据的展示与未来扩展保留。战斗结算不读取词缀文本，不执行受击反制、回合末持续效果、自主行动或牌堆运转；词缀描述的机制在静态规则引擎落地前不会发生。词缀结构校验辅助函数已移除，当前只保留数据。

**一个列表元素只装一条单行规则。** 多值列表的语义是「多条独立规则」，不是「一条长文本」；叙事与心理描写不写进词缀文本，那是 `description` 的职责。

→ 参见：[战斗管道（Combat Pipeline）](combat-pipeline.md)

---

## 生命周期流转（计算端消费）

`playable` / `exhaust` / `retain` / `ethereal` / `transferable` 控制牌在牌堆间的确定性流转，每个标志单一职责：

- `playable`：不可出时在出牌执行端拦截。
- `exhaust`：出牌后永久离场，不进弃牌循环。
- `retain`：回合末保留，跨回合存续。
- `ethereal`：pass turn 时若仍在手牌则自动离场。
- `transferable`：出牌时按命中分配额外投递副本；副本落地即 `transferable=False`、只传一跳。目标经 `target_type` 解析，副本数等于该角色在解析目标列表中的出现次数：`SPREAD` 的列表就是命中分配，`SINGLE` / `ALL` / `SELF` 则各一份。

组合这些标志可表达「一次性爆发」「常驻被动」「转嫁载体」等玩法；互斥与依赖是硬约束。


---

## 牌堆变更对谁可见

判据是「谁的容器动了」，而不是「谁触发的动作」：牌库、抽牌堆、手牌、弃牌堆、消耗堆任一处发生变更，就写一条只给容器主人的说明。自己抽牌会收到记录，别人打出 `transferable` 牌把副本塞进我的手牌同样会收到。

决策与事实分层记录，互不替代：出牌是决策，牌最终落在弃牌堆还是消耗堆是事实。队列增减是私人信息，只写给本人；「某人打出了什么」仍照常广播。需要查看当前牌堆内容时，用 `read_piles` 工具按需拉取。

→ 参见：[战斗管道（Combat Pipeline）](combat-pipeline.md)

---

## 来源引用（source）

`source` 记录牌来源（生成/注入者）的名称：预置牌为角色自身，装备物化牌为发起行动者。它既是追溯手段，也是 `transferable` 副本保留来源的依据；当前不参与词缀条件判定。

装备物化牌的归还回链由装备侧登记组件在战斗结束后统一处理。

→ 参见：[装备系统（GearItem）](gear-item.md)

---

## 设计决策

当前分层是「确定性骨架 + 保留的词缀数据」：战斗循环只依赖目标、流转、能量、死亡这些确定性字段；词缀作为未来规则引擎的数据基础保留，但不再由 LLM 在结算时临场解释。这样结算可复现、日志与数值同源，同时不丢掉已经生成的内容形状。

# 角色计划（Actor Plan）

## 结论

计划是角色在一轮里「想」，不是「做」。它读的是这一刻的舞台环境与在场角色，产出是一组工具调用；工具当前全部空转，世界状态不变，唯一留下的痕迹是这个角色记忆里那次对话。

## 为什么是一个 system 加一个动作

行动与思考分成两步：谁该想、想完做什么，都由外部决定。系统只负责「给谁想、给什么上下文、把结果记下来」。要推动某个角色，就给它挂一个只在当轮有效的动作组件；决定挂谁的代码在 system 之外。

开发期由 CLI 点名推动——一次可以指定一个或多个角色。谁都没被点名时，这个系统一次也不会跑。自主运行（每轮自动决定谁该行动）属于玩法策略，不属于这里；那条策略落地时会复用同一个动作，只是判定谁该挂它。

## 上下文里放什么

任务提示词只放三样：当前舞台、环境快照、在场角色（含各自的外观快照）。这些信息都在本系统之前的一轮里刷新过，所以计划看到的是这一轮的样子，而不是上一轮。

计划是一个 agent loop，可以用多个工具表达连续行为；轮次上限很小，够「说一句、走一步」，又不会让模型自己绕圈。

## 行为以工具表达

说话与移动现在是空转的工具：打日志、返回回执，不改世界。回执告诉模型「已记下」，否则它会为同一件事反复调用。

工具的语义归这个 system 所有，所以定义与处理函数都放在系统内部——它们是这个系统在「这一刻」能发起的行为，不是通用工具库的一部分。等行为真正生效时，改动也只落在这里。

## 失败就是轮空

计划失败（请求异常、循环中止）只记一条警告：这个角色本轮没有行动，下一次被点名时再想。它不抛给 pipeline，也就不触发整次 pass 的回滚——思考失败不该让世界倒退。

这条边界与描述刷新一致：预期内失败由 system 自己消化。

→ 参见：[System 错误处理与回滚边界](system-error-handling.md)

## 边界

计划不改组件、不改世界、不发布领域事件，读的是记忆与描述组件的当前值。因此它必须排在描述刷新之后，否则计划看到的会是尚未刷新的旧描述。

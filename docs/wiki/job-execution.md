# Job 执行与事件日志（Job Execution）

`Job` 是一次可由服务端异步执行的业务动作，使用 Procrastinate 的 job id 作为唯一标识。Procrastinate 只管排队与执行状态；执行过程由 `job_events` 记录，运行状态由整块快照承载。三者合起来构成客户端的 job 视图。

## 设计意图

- **job 是执行单元，不是领域历史**：一次动作对应一个 job；它回答「这次执行走到哪、哪个 system 失败」，不承载玩家可见的完整叙事。
- **队列状态不复制**：job 的排队/执行/终态仍以 Procrastinate 为准，不另建一套状态枚举或状态表。
- **过程可观察**：pipeline 在每个 system 边界写入开始、结束、耗时与失败事件；失败时不用等终态就能定位到具体 system。
- **失败可定位**：失败默认中断本次 pass 并记录具体 system；显式声明为旁路的 system 失败后记录并继续。显式提前结束是控制流，不算失败。
- **失败可回滚**：每个 pass 开始前追加一条整块快照；失败时 ECS 与 agent 记忆一起回到该快照。快照行保留为历史，供审计与再次回滚。
- **会话不回滚**：用户会话历史独立于 job，失败尝试仍保留在上帝视角中，以 `job_id` 与 job 结果关联。

## 执行链路

动作接口只负责派发并返回 job id。worker 执行 job 时依次：

1. 绑定当前 job 上下文；
2. 记录 job 开始；
3. 进入玩家房间事务，把后续领域事件关联到该 job；
4. 追加运行前快照（ECS 与 agent 记忆成对写入），得到本次执行的基线；
5. 推动唯一全局 pipeline；pipeline 观测器逐 system 写入开始/结束/失败；
6. 成功后记录 job 成功；
7. 失败时把 ECS 与 agent 记忆回滚到快照，并重建 pipeline（旧分组与反应式收集器在回滚后失效），再记录 system/job 失败并原样上抛。

快照写入发生在 pass 之前：即使执行失败，这条历史也保留，恢复与重放都以它为准。真正的失败不会吞掉原始异常；回滚自身失败只记录，不覆盖首个错误。

## 与客户端

- 批量状态查询只返回精简 job 状态。
- 单个 job 查询返回状态与完整事件。
- 事件接口支持按事件 id 增量读取，适合长任务轮询。
- SSE 监听在终态结束；取消与中止也视为终态，不会被当作永久运行。
- job 事件中的失败摘要面向客户端，完整异常栈留在服务端日志。

## 与其他系统的关系

- job 事件记录技术过程；会话历史记录玩家可见的领域历史；两者通过 job 标识关联，不合并。
- 快照由持久化层按追加方式保存，ECS 与 agent 记忆是平级系统，必须由同一编排一起回滚。
